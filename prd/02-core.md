# 02. core

core は Rust 製の単一バイナリで、**統計の収集**と **REST API** を担う。

**実装済みの範囲**: §収集 〜 §REST API（現行）は実装済みである。§計画中の API は未実装、
§gap は現行実装の既知の問題である。

## プロセスの構成

起動時にログファイルを読んでキャッシュを復元し、そのあと 2 本のスレッドを動かす
（`core/src/main.rs`）。

| スレッド | 役割 | 実装 |
|---|---|---|
| logger | 10 秒ごとに統計を集め、ログに追記し、キャッシュに積む | `core/src/log.rs` |
| server | `0.0.0.0:7878` で REST API を返す | `core/src/server.rs` |

両者は `SharedUsageCache`（`Arc<RwLock<UsageCache>>`）を共有する。logger が write ロック、
server が read ロックを取る。

server スレッドは接続を受け付けるだけで、リクエストの処理は**接続ごとに起こす短命のスレッド**が
行う（§REST API（現行））。

## 収集

**Docker Engine API を `/var/run/docker.sock` 越しに叩く。** HTTP クライアントは使わず、
Unix ソケットにリクエスト文字列を直接書き込む（`call_docker_api`）。

10 秒ごとの 1 回の収集（tick）で、次の順に呼ぶ。

1. `GET /containers/json` — 動いているコンテナの一覧。`Names[0]` から先頭の `/` を除いたものを
   **コンテナ名**として以後の識別子に使う。
2. コンテナごとに `GET /containers/{name}/stats?stream=false&one-shot=true` — 統計の瞬間値。

**送るのは GET だけである。** コンテナを操作する API は呼ばない（[00](./00-product.md) §非目標）。

レスポンスの解釈は簡略化している。ヘッダは読まず、**`{` または `[` で始まる最初の行**を
JSON の本体として扱う。Docker が返す形に依存した実装であり、チャンク転送などには対応しない。

tick は壁時計の 10 秒境界に揃える。処理に時間がかかっても次の tick の時刻はずれない。

**1 つのコンテナの不調で、その tick の他のコンテナを捨てない**（`collect_stats`）。

- ⚠ Docker は稀に `read` が `0001-01-01T00:00:00Z` の統計を返す。その tick では、
  **該当コンテナだけ**を飛ばす。`read` を解釈できない場合も同じである。
- 統計の取得に失敗したコンテナも、そのコンテナだけを飛ばす。
- コンテナの一覧（手順 1）を取れなかった場合は、その tick 全体を飛ばす。

**logger は一時的な失敗では止まらない**（`run_tick`）。一覧の取得、ログへの追記、
現在時刻の取得のどれかが失敗した tick は、エラーを標準エラー出力に出して何も記録せず、
次の tick へ進む。失敗しても tick の時刻（10 秒境界）は進める。同じ失敗が続けば、
tick のたびにエラーが出力される。logger が止まるのは、起動時の準備（`./log` の作成など）に
失敗した場合だけである。

ログへの追記に失敗した tick は、キャッシュにも入れない。ログとキャッシュの内容を
揃えるためである。

## 使用率の算出

Docker が返す値の多くは**積算値**である。使用率は**前回の tick との差分**から求める
（`calc_usages`）。そのため、起動後の最初の tick は記録されない。

**経過時間は実測する。** コンテナごとに、Docker が返した `read` の時刻の差
（今回 − 前回）を経過時間として使う。設定上の間隔（10 秒）では割らない。
tick が 1 回飛んで前回から 20 秒空いた場合も、速度は 20 秒で割った値になる。

| 項目 | 算出 | 単位 |
|---|---|---|
| CPU | `Δtotal_usage / Δsystem_cpu_usage × online_cpus × 100` | % |
| メモリ | `(usage − stats.cache) / limit × 100` | % |
| IO read / write | `Δbytes / 経過ミリ秒`（= kB/s） | kB/s |
| ネットワーク recv / send | `Δbytes / 経過ミリ秒`（= kB/s） | kB/s |

- CPU の `total_usage` と `system_cpu_usage` は ns で届き、ms に丸めてから差を取る。
  全コアを使い切ると `online_cpus × 100` % になる（`docker stats` と同じ流儀）。
  差分同士の比なので、経過時間は式に現れない。
- メモリは差分を取らない瞬間値である。`stats.cache` が無い場合は 0 として扱う。
- IO は `blkio_stats.io_service_bytes_recursive` のうち、`op` が `read` / `write` である
  **最初の要素**の値を使う。
- ⚠ **ネットワークは `networks.eth0` だけを読む。** 複数のネットワークに属するコンテナでは、
  `eth0` 以外の通信量が数字に入らない。
- IO とネットワークは**整数の kB/s**（切り捨て）で持つ。
- 元の値が取れなかった項目は `null` になる。分母が 0 で比を求められない場合も `null` にする。

次のコンテナは、**その tick では記録しない**（他のコンテナは記録する）。

- 統計を採れなかったコンテナ（§収集）。
- 前回の統計が無いコンテナ。新しく起動したコンテナが該当し、次の tick から記録される。
- `read` の時刻が前回から進んでいない（差が 0 以下の）コンテナ。

記録できるコンテナが 1 つも無い tick は、ログにもキャッシュにも何も書かない。

**前回の統計は、採れなかった tick をまたいで持ち越す**（`carry_over_stats`）。

- その tick の一覧に載っているが統計を採れなかったコンテナは、前回の統計をそのまま残す。
  次に採れた tick で、`read` の時刻の差を経過時間として 1 点を記録する。
  1 回の不調で欠ける点は 1 つで、復帰後の速度は実際の経過時間で割った値になる。
- 統計は採れたが `read` の時刻が前回から進んでいない（同じ、または戻った）コンテナも、
  前回の統計をそのまま残す。その tick は記録されないので、置き換えると積算値の増分が
  記録から落ちるためである。次に時刻が進んだ統計が来たとき、最後に記録できた値からの
  差分と、その時刻の差で 1 点を記録する。
- ただし、**時刻が進まない統計が同じコンテナで 3 tick 続いたら、3 回目で 1 点を記録し、
  前回の統計を今回の値に置き換える**（`MAX_STALLED_TICKS`）。時計が大きく巻き戻された場合や、
  Docker が同じ統計を返し続ける場合に、記録が止まり続けないようにするためである。
  - この 1 点の差分は、最後に記録できた統計から今回の統計までである。そこまでの増分は
    記録から落ちない。
  - `read` の時刻の差は使えない（0 以下）ので、経過時間には **core 自身が測った時間**を使う。
    前回の統計を採った時点から今回までの、単調時計での差である。Docker の時刻の差を
    使わないのは、この 1 点だけである。
  - その次の tick からは、`read` の時刻の差で通常どおり記録する。
  - 回数はコンテナごとに数え、時刻が進んだ統計が来たら 0 に戻す。
  - 統計を採れなかった tick は、回数に数えず、0 にも戻さない。
  - 一覧に載っていないコンテナは、回数も捨てる。
- ログへの追記に失敗した tick では、前回の統計を進めない。その tick の増分は、
  次に記録できた点に含まれる。
- 一覧の取得に失敗した tick では、全コンテナの前回の統計を残す。
- その tick の一覧に載っていないコンテナは、前回の統計を捨てる。止まったコンテナの値を
  持ち続けない。同じ名前で再び現れた場合は、新しいコンテナと同じ扱いになる。
- 積算値が前回より小さい場合（コンテナの再起動でカウンタが戻った場合など）は、
  差分を 0 として扱う。

## ログ形式

`./log/log_daily` に **JSONL**（1 tick が 1 行）で追記する。行末は `\r\n` である。

```json
{"time":"2026-01-01T00:00:10.023034093Z","millis":10000,"stats":{
  "web":{"cpu":{"percentage":0.03,"total":3,"system":19860,"ncpu":2},
         "memory":{"percentage":3.64,"used":36696064,"available":1007222784},
         "io":{"readkB":4161,"writekB":48689,"readkBps":0,"writekBps":0},
         "net":{"recvkB":4,"sendkB":0,"recvkBps":0,"sendkBps":0}},
  "db":{ ... }}}
```

（実際は 1 行。`web` `db` は例示用の仮のコンテナ名である）

- `time` は Docker が返した `read` の値（UTC、ナノ秒精度の ISO 8601）をそのまま書く。
  **その tick で記録するコンテナのうち、時刻が最も早いもの**を全コンテナに使う
  （飛ばしたコンテナの時刻は使わない）。`read` の時刻が前回から進んでいないコンテナの時刻は、
  ほかに記録するコンテナが無いときだけ使う。
- `millis` は tick の間隔（設定値の 10000）である。実測の経過時間ではない。
- 小数は 2 桁に丸める。整数はそのまま出す。
- `total` / `system` は ms 単位の**差分**、`readkB` などの `kB` は**積算値**である。

### ログの保持

**ログファイルのローテーションは core の責務ではない。** ホスト側の logrotate が
24 時間ごとに回す（[05](./05-deploy.md)）。

core は**書き込みのたびにファイルを開き直す**（`log_daily` が毎回 `OpenOptions` で開く）。
このため、外部から rename されても次の書き込みは新しいファイルに向かう。
🔒 **ファイルハンドルを保持し続ける実装に変えない。** 変える場合はローテーションとの
連携（再オープンの契機）を合わせて設計する。

core 自身はファイルを切り詰めも削除もしない。ローテーションが無ければファイルは伸び続ける。

**週・月単位への要約は検討中である。** 日次のログを週次・月次へ要約しながら繰り上げる
構想があるが、形は決めておらず、約束もしない。

## キャッシュ

直近のデータはメモリ上に持つ（`core/src/log_cache.rs`）。API はこのキャッシュだけを読み、
ログファイルは読まない。

- **1 tick・1 コンテナを 1 つの小さな構造体にまとめる**（`UsagePoint`）。コンテナごとに
  `VecDeque` を 1 本持つ。
- 持つのは時刻と表示に使う値だけである（CPU / メモリの `percentage`、
  IO の `readkBps` / `writekBps`、ネットワークの `recvkBps` / `sendkBps`）。
- **時刻は文字列ではなく、エポックからのミリ秒（整数）で持つ。** 文字列のまま種別ごとに
  持つと 24 時間分で 1 コンテナあたり数 MB になり、メモリの上限
  （[01](./01-architecture.md) §設計方針）に収まらなくなる。ISO 8601 との変換は
  自前で行う（`core/src/time.rs`）。ミリ秒より細かい桁は切り捨てる。
- **窓は時間で切る。** キャッシュ全体で最新の点の時刻を基準に、**24 時間より古い点を捨てる**。
  安全のため、1 コンテナあたり**最大 8640 点**（`MAX_LOG_LENGTH`。24 時間 × 10 秒間隔）の
  上限も掛ける。
- **稼働中は、現在時刻も基準に加える**（最新の点の時刻と現在時刻の、遅い方から数える）。
  tick のたびに、記録の有無や成否に関わらず捨てる処理を掛ける。新しい点が 1 つも
  来ない間（全コンテナが止まっている、収集に失敗し続けている）も、古い点は時間の経過で消える。
- 捨てる処理は、その tick でデータが来なかったコンテナにも掛かる。
  **点が 1 つも無くなったコンテナはキャッシュから消える。** 止まったコンテナは、
  止まってから 24 時間で `/containers` の一覧から消える。
- 1 コンテナの系列は時刻の昇順に保つ。そのコンテナの最新の点より新しくない点は、
  追加せずに捨てる。

**起動時にログファイルの末尾 8640 行を読んで復元する**（`read_log`）。
再起動してもグラフが空にならないことが狙いである。

- **ログファイルが無ければ、キャッシュが空のまま起動する。** 無いこと以外の理由で
  読めない場合は、起動に失敗する。
- 復元にも同じ窓を掛ける。ログの最後の行から 24 時間より古い行は、キャッシュに残らない。
  復元の時点では現在時刻を基準に加えない。現在時刻から見て古い点は、起動後の最初の tick で消える。
- **読めない行は、その行だけを飛ばして続きを読む。** JSON として解釈できない行、
  `time` を解釈できない行、`time` が `0001-01-01T00:00:00Z` の行が該当する
  （過去のログには、この時刻で書かれた行が含まれる）。

## ダウンサンプリング

API は 1 系列を**最大 512 点**（`DownsampleOption` の既定値）に間引いて返す
（`UsageCache::downsample`）。点数が 512 以下ならそのまま返す。

方式は **LTTB（Largest Triangle Three Buckets）**である。
先頭と末尾を除いた点をバケットに分け、各バケットから「直前に選んだ点・候補・
**次のバケットの平均点**」の作る三角形の面積が最大になる点を 1 つ選ぶ。
山や谷が残りやすく、見た目の情報量が落ちにくい。

🔒 **等間隔の間引きや平均化に置き換えない。** スパイクが消えると、
この道具の目的（いつ重かったかを見る）が損なわれる。

- **先頭と末尾の点は必ず残す。**
- 横軸は**系列の先頭の点からの経過秒**である。日付をまたいでも単調に増える。
- 縦軸は系列の値で、欠損（`null`）は 0 として扱う。
- **系列ごとに独立して選ぶ。** 同じコンテナでも、cpu / memory / read / write / recv / send の
  どれを基準にするかで残る点が変わる。

## REST API（現行）

`GET` のみを受け付ける。成功時のレスポンスは `Content-Type: application/json` である。

| パス | 返すもの |
|---|---|
| `/containers` | コンテナ名の配列（**アルファベット順**） |
| `/containers/{name}/cpu` | `[{"time": string, "percentage": number \| null}, ...]` |
| `/containers/{name}/memory` | 同上 |
| `/containers/{name}/io/read` | `[{"time": string, "readkBps": number \| null, "writekBps": number \| null}, ...]` |
| `/containers/{name}/io/write` | 同上 |
| `/containers/{name}/net/recv` | `[{"time": string, "recvkBps": number \| null, "sendkBps": number \| null}, ...]` |
| `/containers/{name}/net/send` | 同上 |

- **`io/read` と `io/write` は同じ形の要素を返す。** 違いは**ダウンサンプリングの基準にする値**
  （read か write か）であり、選ばれる点が変わる。`net/recv` と `net/send` も同じである。
- `/containers` の順序は web の色割り当てが依存している（[03](./03-web.md) §色）。
- `time` は UTC の ISO 8601 文字列（`Z` 終端）で、**ミリ秒精度**である
  （例: `2026-01-01T00:00:10.023Z`）。ログの `time`（ナノ秒精度）からミリ秒未満を
  切り捨てたものにあたる。
- 数値は、小数を 2 桁に丸め、整数はそのまま出す。欠損は `null` である。

| 状況 | ステータス |
|---|---|
| リクエスト行を解釈できない / リクエスト行が 1024 バイトを超える | 400 |
| `GET` 以外 | 405 |
| 経路に一致しない / 知らないコンテナ名 / 知らない種別 | 404 |
| 処理中のエラー | 500（本文は固定の文言） |

- エラー応答は `Content-Type: text/plain` で、本文を持つのは 500 だけである。
- 🔒 **500 の本文は固定の文言にする。** 内部のエラー文字列は標準エラー出力にだけ出し、
  応答には載せない（[04](./04-access-and-privacy.md) §公開してよい情報の線）。
- 全応答に `Content-Length` と `Connection: close` を付ける。
- 何も送らずに閉じられた接続には、何も返さない。

HTTP の扱いは最小限である。リクエストは**1 行目**（メソッドとパス）しか読まず、
ヘッダは無視する。クエリ文字列は解釈しない（クエリを付けたパスは 404 になる）。
1 接続につき 1 リクエストで、keep-alive はしない。

接続の扱いは次のとおりである（`core/src/server.rs`）。

- **接続ごとにスレッドを起こす。** 1 本の接続の遅延や失敗は、他の接続に波及しない。
- **同時に処理するのは 16 本まで**である。超えた接続は断らず、枠が空くまで待たせる
  （待っている接続は OS の backlog に並ぶ）。メモリの上限（[01](./01-architecture.md) §設計方針）の
  中でスレッド数が膨らまないようにするためである。
- **読み書きのタイムアウトは 5 秒**である。リクエスト行を読み切るまでの合計も 5 秒で打ち切り、
  その場合は何も返さずに閉じる。
- 何も送らない接続が 16 本で枠を埋めると、タイムアウトで枠が空くまで（最長 5 秒）
  他の接続は待たされる。これは受け入れている性質である。
- **1 本の接続で起きたエラーでは待ち受けを止めない。** エラーは標準エラー出力に出して、
  次の接続を受け付ける。接続の受け付けそのものが失敗した場合も同じである。
- 1 バイトも受け取らずに終わった接続（すぐ閉じられた、無言のままタイムアウトした）は、
  エラーとして出力しない。

## 計画中の API: bulk endpoint

**全コンテナ分を 1 回のリクエストで返す API を足す。**

現状、web は 1 回の表示で `/containers` に加えてコンテナ別の API を `6N` 本叩く
（N はコンテナ数。CPU と メモリが各 N、IO と ネットワークが各 2N）。
コンテナが増えるほどリクエストが増え、同時に処理できる 16 本を超えた分は待ち時間になる。

目標は**チャート 1 枚につき 1 リクエスト**である。

- 種別ごとに、全コンテナの系列をまとめて返す。
- ダウンサンプリングの方式と点数は現行と変えない。
- **パスとレスポンスの形は未確定**である（要確認）。コンテナ名をキーにしたオブジェクトで返す形を
  想定している。
- 現行のコンテナ別 API は残す。web が bulk に移ったあとで廃止するかは、そのとき決める。
- web 側の `next/src/lib/fetchers.ts` と各チャートの変更を伴う（[03](./03-web.md)）。

**接続処理の並行化は実装済みである**（§REST API（現行））。web が並列に発射したリクエストは
core でも並列に処理される（同時に 16 本まで。超えた分は順に待つ）。ただしリクエスト数
そのものは減らない。**bulk endpoint は引き続き計画中**であり、リクエスト数を減らす本筋は
こちらである。

## gap（現行実装の既知の問題）

いずれも現状の挙動であり、直すべきものである。

**値の定義**に関するもの:

- ⚠ **メモリ使用率がページキャッシュ込みになりうる。** 式は `usage − stats.cache` だが、
  cgroup v2 の環境では `stats.cache` が返らず、0 として扱われる。その場合、
  ページキャッシュを含んだ値がそのまま使用率になる。
- ⚠ **IO とネットワークは 1 kB/s 未満が 0 になる。** 整数の kB/s に切り捨てて持つためで、
  少量の通信や書き込みが続いていてもグラフには現れない。
- ⚠ **IO とネットワークは一部しか数えない。** ネットワークは `eth0` だけ、IO は最初の
  read / write の要素だけを読む（§使用率の算出）。

**キャッシュと復元**に関するもの:

- ⚠ **時計が大きく未来に飛んだ点が入ると、以後の正常な点が捨てられる。** 窓の基準が
  「キャッシュ全体で最新の点の時刻」であるため、正常な時刻の点が窓の外として扱われる。
  その点はログにも残るので、再起動しても復元され、ログのローテーションまで続く。
  tick の時点で時計が未来に飛んでいた場合も、その時点のキャッシュは古い点として捨てられる。
- ⚠ **時計が巻き戻されると、追いつくまでキャッシュに点が入らない。** 前回の統計の置き換え
  （§使用率の算出）でログへの記録は 3 tick 目から続くが、キャッシュは 1 コンテナの系列を
  時刻の昇順に保つため、そのコンテナの最新の点より新しくない点を捨てる。時計が巻き戻す前の
  時刻を追い越すまで、グラフは伸びない。ログには残る。
- **`time` が `0001-01-01T00:00:00Z` の行は、tick ごと復元されない。** その行に含まれる
  他のコンテナの値も失われる。過去のログに限った話で、今後は書かれない。
- **復元は末尾 8640 行だけを解釈する。** その中に飛ばされる行が混じると、
  ファイルにそれより前の行が残っていても、復元される点数がその分だけ減る。

**テスト**に関するもの:

- **Docker ソケットとログファイルに触れる部分にはテストが無い。** 時刻の変換・使用率の算出・
  ログの復元・キャッシュ・ダウンサンプリング・REST API にはテストがある（`cargo test`）。
  ソケットへの問い合わせ（`call_docker_api`）、コンテナ一覧の解釈、ログへの追記、
  tick を刻むループそのもの（`log_json`）は対象外である。
