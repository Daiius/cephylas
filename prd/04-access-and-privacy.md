# 04. 公開範囲とアクセス制限

本章は、**何を見せてよいか**と**誰に見せるか**を定める。

**実装済みの範囲**: §公開してよい情報の線は現状のとおりである。§アクセス制限は、
**web 側の準備（サービストークンのヘッダを付ける処理）だけが実装済み**である。
Cloudflare Access の導入そのものは**計画中**で、現状は画面も API も制限が無い。

## 現状

- **画面**（`https://<frontend-domain>`）は認証なしで誰でも開ける。
- **API**（`https://<api-domain>/cephylas/*`）も認証なしで誰でも叩ける。

これは**意図した公開**である。作品として見せる性格があり、見えて困る情報を載せていないことを
前提にしている。その前提を次の節で線として定める。

## 公開してよい情報の線

🔒 **API と画面に載せてよいのは、コンテナ名と、その使用率の数値・時刻だけである。**

| 載せてよい | 載せない |
|---|---|
| コンテナ名 | イメージ名・タグ・ダイジェスト |
| CPU / メモリの使用率（%） | 環境変数・ラベル・起動コマンド |
| IO / ネットワークの速度（kB/s） | ポートの割り当て・IP アドレス・ネットワーク名 |
| 計測時刻 | マウント・ボリュームのパス |
| | ホスト名・ホストのスペック・Docker のバージョン |

Docker Engine API は右の列の情報もすべて返す。core は必要な項目だけを取り出しており
（[02](./02-core.md) §収集）、**Docker のレスポンスをそのまま外へ流す実装にしない。**

- 🔒 **エラー応答に内部の情報を載せない。** 500 応答の本文は固定の文言であり、
  内部のエラー文字列は core の標準エラー出力にだけ出す（[02](./02-core.md) §REST API（現行））。
  エラー文字列にはファイルパスなどが含まれうるためである。
- コンテナ名そのものが構成を示す情報である（何のアプリが同居しているかが分かる）。
  現状はこれを公開情報として受け入れている。アクセス制限を入れる動機の 1 つである。
- ログファイル（`log/log_daily`）には API より多い項目（メモリの絶対量、CPU 数など）が入る。
  **ログファイルは配信しない。**

## アクセス制限

**Cloudflare Access で、画面と API の両方を制限する（計画中）。**
web 側の準備だけを先に実装している（§web 側の準備（実装済み））。

```
[Browser] ──①──► [Next.js on Vercel] ──②──► [nginx → core on VPS]
```

| 経路 | 制限の形 |
|---|---|
| ① 画面 | Access のログインを通った者だけが開ける |
| ② API | Access のサービストークンを持つ Next.js だけが叩ける |

- **アプリ自身は認証を実装しない**（[00](./00-product.md) §非目標）。検証は Cloudflare が行い、
  core に届くリクエストは通過済みのものだけになる。core のコードは増やさない。
- **② を伴わない ① は意味を持たない。** 画面を閉じても、API を直接叩けば同じデータが取れる。
  入れる順序は ② を先か、同時にする。
- **オリジンへの直接到達を塞ぐ。** Cloudflare を経由せずに VPS へ届く経路が残っていると、
  Access を迂回できる。塞ぎ方（トンネル、送信元の制限など）は運用側で決め、ここには書かない。
- **ビルド時の取得に注意する。** `/` は Partial Prerender で、ビルド中にも core への fetch が走る。
  トークンが無い環境でのビルドが失敗しないこと（取得失敗は「取得中...」の表示に落ちる現状の
  挙動）を保つ。
- 設定値・ポリシー・トークンは PRD に書かない。`.claude/local/` に置く。

### web 側の準備（実装済み）

**web は、core への fetch に Access のサービストークンのヘッダを付けられる。**
環境変数が未設定なら何も付けず、Access を導入する前の動作と変わらない。

| 環境変数 | 付けるヘッダ |
|---|---|
| `CF_ACCESS_CLIENT_ID` | `CF-Access-Client-Id` |
| `CF_ACCESS_CLIENT_SECRET` | `CF-Access-Client-Secret` |

- **両方が空でない値で設定されているときだけ、2 つのヘッダを付ける。** 対象は core への
  すべての fetch である（`/usages/{kind}` と、古い core 向けの互換の経路の全リクエスト。
  [03](./03-web.md) §データ取得）。
- **どちらも未設定なら、ヘッダを付けず、何も出さない。**
- **片方だけ設定されているときは、ヘッダを付けず、サーバ側のログに警告を出す。**
  設定の誤りに気づくためである。警告はプロセスにつき 1 回で、値は含めない。
- **値にヘッダとして送れない文字（改行、空白、ASCII 以外）が含まれるときも、ヘッダを付けず、
  同じ形で警告を出す。** そのまま fetch に渡すと例外になり、その文言に値が入りうるためである。
  値の前後の空白は取り除いてから判定する。
- 🔒 **ヘッダを付けるリクエストでは、リダイレクトを追わない**（`redirect: 'manual'`）。
  独自のヘッダは別オリジンへのリダイレクトにも転送されるので、追うとトークンが core 以外の
  宛先へ渡りうるためである。3xx の応答は「2xx 以外のステータス」として扱う
  （`/usages/{kind}` なら互換の経路へ切り替え、互換の経路なら失敗）。
  ヘッダを付けないとき（未設定、片方だけ、送れない値）は、これまでどおりリダイレクトを追う。
  ヘッダとリダイレクトの指定は、同じ 1 か所で組にして作る。
- ヘッダの組み立ては `next/src/lib/core-fetch.ts` の 1 か所にまとめている。
  core へのリクエストは、必ずここの `coreFetch` で送る（付け忘れた経路を残さない）。
  同じ場所で、fetch の期限も付ける（[03](./03-web.md) §データ取得）。
  ヘッダ・リダイレクトの指定・期限を、呼び出し側で別々に指定しない。
- 🔒 期限切れのエラーの文言は固定で、URL もトークンの値も含まない。
- 🔒 **環境変数はサーバ側でだけ読む。** `NEXT_PUBLIC_` を付けない。クライアントコンポーネントから
  import されるモジュールに、環境変数を読むコードを置かない。
- 🔒 **トークンの値を、ログ・エラーメッセージ・取得関数の戻り値・クライアントへ渡す props の
  どこにも含めない。** `'use cache'` の関数の戻り値（シリアライズされて cache される）にも含めない。
  値を渡す先は、fetch のヘッダだけである。
- core は変更しない。ヘッダを検証するのは Cloudflare であり、core はこのヘッダを見ない。

### Access の導入（計画中）

次は運用側（リポジトリの外）の作業であり、**いずれも未実施**である。

- **Cloudflare 側の設定。** 画面と API のそれぞれに Access を掛け、API にはサービストークンを
  許可するポリシーを置く。
- **Vercel の環境変数の設定。** 上の 2 つの環境変数に、発行したサービストークンを設定する
  （[05](./05-deploy.md) §本番の形）。設定するまで、web はヘッダを付けない。
- **オリジンへの直接到達を塞ぐこと**（上記）。

## gap

- **制限は未導入である。** 実装済みなのは web 側の準備だけで、現状は画面も API も開いている。
  環境変数を設定していないので、web はヘッダを付けていない。
- ⚠ **リポジトリ内のログには、実際のコンテナ名が入っている。** `log/log_daily` は
  本番で採ったログをそのまま置いたもので、[README](./README.md) §公開リポジトリでの秘匿方針の
  「コンテナ名を文書に書かない」と食い違う。追跡対象から外すのがあるべき姿である。
  ただし本番でも同じパスに稼働中のログを書いているので、本番の配置手順と合わせて行う必要がある
  （[05](./05-deploy.md) §リポジトリ内のログ）。git の履歴には残る。
- ⚠ **`core` は `0.0.0.0:7878` で待ち受ける。** `compose.yml`（本番も読む）が、このポートを
  ホストに公開している。本番でその先をどこまで外へ出しているかは運用側の設定であり、要確認。
