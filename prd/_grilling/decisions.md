## PRD の新設（2026-10-14 の grill）

cephylas には PRD が無く、仕様は `CLAUDE.md`・`README.md`・`core/README.md`・`TASKS.md` と
紹介記事に散らばっていた。事実はそれらと現行コードから起こし、コードから決められない点だけを
ヒアリングで決めた。

紹介記事（2024-12）の構成図は「Next.js がログファイルを直接読む」当時のものである。
記事は動機と設計思想の出典として使い、構成は現行コードを正とした。

### Q1. 認証なしで見える現状の位置づけ → **意図した公開。後から Cloudflare Access で制限する**

作品として見せる性格があり、現状の公開は欠陥として扱わない。そのかわり、
「載せてよいのはコンテナ名と使用率だけ」という線を明文化した（[04](../04-access-and-privacy.md)）。
制限は計画中として書く。

### Q2. 実ドメインの扱い → **PRD も既存の文書もプレースホルダに揃える**

`CLAUDE.md`・`TASKS.md`・`fetchers.ts` のコメントに実ドメインが書かれていた。
git の履歴に残るので消しても秘匿にはならないが、現行の文書を他リポジトリと同じ規則で
読めることを優先した。実値は `.claude/local/` へ退避した。

あわせて、**`TASKS.md` を git 管理から外した。** 進行状況は時間とともに変わる情報で、
リポジトリに固定しない方がよいという最近の運用に合わせた。置き場は `.claude/local/TASKS.md` とし、
`.claude/local/.gitignore`（`*` の 1 行）とルートの `.gitignore` の二重で除外する。

### Q3. ログの保持 → **ローテーションはホスト側の logrotate（24 時間）が担う**

core にはローテーションの実装が無く、追記し続けるだけである。運用ではホスト側の logrotate で
24 時間ごとに回している。これを「core の責務ではない」と明記し、core が書き込みのたびに
ファイルを開き直す性質を、ローテーションと組むための条件として書いた（[02](../02-core.md)）。

週・月単位への要約（`core/README.md` にあった構想）は、ヒアリングでは決めていない。
約束しない「検討中」として置いた。

### Q4. core の「crate は json のみ・HTTP 手書き・メモリ 50MB」→ **方針として書くだけ**

不変条件にはしない。「軽量・依存最小を優先する」という姿勢として書き、
レビューが crate の追加を違反として指摘する形にはしない（[01](../01-architecture.md) §設計方針）。

### Q5. core の API のあるべき姿 → **bulk endpoint を目標にする**

1 回の表示で web が発射するリクエストが多いことが問題の根である。接続処理の並行化では
本数が減らないので、全コンテナ分を 1 回で返す API を計画中とし、並行化は任意の改善に留めた。
この時点では、パスとレスポンスの形は決めていなかった。

（その後）`GET /usages/{kind}` として実装し、web も切り替えた。接続処理の並行化も、
不正な接続で API が止まる問題を直す過程で入った。形は [02](../02-core.md) §REST API（現行）を参照。

### Q6. Cloudflare Access の掛け先 → **画面と API の両方**

画面だけを閉じても API を直接叩けば同じデータが取れるため、両方を対象にした。
API はサービストークンを持つ Next.js だけが叩ける形とし、オリジンへの直接到達も塞ぐ。
アプリ自身には認証を実装しない。

### 古い文書の整理 → **`nginx.conf` も現行構成に合わせて直す**

`core/README.md` には、すでに捨てた `/proc` 方式の図が残っていた。`README.md` の設計の節は
PRD と重複していた。どちらも PRD へのリンクに置き換えた。

`nginx.conf` は、Next.js を VPS で動かしていた頃の内容（Next.js への中継）のままだった。
core への中継だけに書き直した。**本番 VPS の実設定との突き合わせはしていない。**
配置する前に、実際に動いている設定と見比べること。
