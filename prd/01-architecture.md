# 01. アーキテクチャ

**実装済みの範囲**: 本章の構成はすべて実装済みである。未実装の部分は各節で「計画中」と明示する。

## 構成要素

| 要素 | 置き場所 | 役割 |
|---|---|---|
| **core** | VPS 上のコンテナ | 統計の収集、ログへの追記、メモリ上のキャッシュ、REST API（`:7878`） |
| **web** | Vercel | Next.js。Server Component から core の API を叩き、Chart.js で描画する |
| **nginx** | VPS 上のコンテナ | `https://<api-domain>/cephylas/*` を core へ中継する |

core は 1 プロセスの中で 2 本のスレッドを動かす。**logger** が 10 秒ごとに統計を集め、
**server** が REST API を返す。両者はメモリ上のキャッシュを `Arc<RwLock<...>>` で共有する
（[02](./02-core.md)）。server は接続を受け付けるたびに、その接続を処理する短命のスレッドを起こす。

## 通信の向き

🔒 **ブラウザが話す相手は Next.js だけである。** core の API を叩くのは Next.js のサーバ側
（Server Component）だけで、API の URL はブラウザに渡さない。

- 環境変数 `API_URL` はサーバ側だけで読む（`NEXT_PUBLIC_` を付けない）。
- クライアントコンポーネントから core を直接 fetch するコードを書かない。

この線を引く理由は 2 つある。API の形を web の都合で自由に変えられること、そして
API 側のアクセス制限を「Next.js だけ通す」という単純な規則にできることである
（[04](./04-access-and-privacy.md)）。

⚠ **現状、本番の core API はインターネットから直接叩ける。** web が Vercel にあるため、
API は VPS の内部ネットワークに閉じられない。「Next.js だけが叩ける」状態にするのは
Cloudflare Access の導入で実現する**計画中**の項目である（[04](./04-access-and-privacy.md)）。

## 責務の分担

**重い処理は core に寄せる。** web は受け取った点列を Chart.js に渡すだけにする。

- **使用率の算出は core が行う。** Docker が返すのは積算値であり、前回との差分と時間間隔から
  使用率に換算する必要がある。
- **ダウンサンプリングも core が行う。** 24 時間分は 1 コンテナあたり最大 8640 点あり、
  そのまま返すと転送量も描画も重い。

初期の実装では Next.js がログファイルを直接読み、差分計算まで行っていた。
1 万行を超える JSONL を Node.js で処理すると、処理時間が約 0.8 秒、メモリが数百 MB に達したため、
計算を core に移した。**この分担を逆戻りさせない。**

`next/src/lib/downsample.ts` には当時の TypeScript 版 LTTB が残っているが、
**どこからも使われていない**。

## リポジトリ構成

```
cephylas/
├── core/                 # Rust（pnpm workspace の外）
├── next/                 # Next.js（workspace 唯一の TS package、name は "web"）
├── log/                  # log_daily の置き場
├── benchmark/            # core の HTTP 実装を比べる負荷試験（workspace の外）
├── prd/                  # この PRD
├── nginx.conf            # 本番 VPS の nginx 設定（dev では使わない）
├── compose.yml           # core の定義（dev と本番の両方が読む）
├── compose.dev.yml       # dev 用の上書き（メモリ制限の緩和、Docker ソケット）
├── compose.prod.yml      # 本番用の上書き（nginx を追加）
├── AGENTS.md             # 開発ガイド（コーディングエージェント共通）
└── CLAUDE.md             # AGENTS.md を読むだけの入口
```

TS package が 1 つしかないため `packages/web/` ではなく `next/` に直接置いている。
複数になったら `packages/` へ移す。

## 設計方針

次は**優先する姿勢**である。破ってはならない制約ではなく、必要なら変えてよい。
変えるときは、この節を先に書き換える。

- **core は軽量・依存最小を優先する。** 現状の外部 crate は `json` だけで、HTTP の送受信も
  標準ライブラリで書いている。crate を足すこと自体は禁止しないが、足す前に
  標準ライブラリで足りないかを考える。
- **core のメモリ使用量を小さく保つ。** 現状は compose で 50MB に制限している。
  同居する他のコンテナを圧迫しないことが目的である。キャッシュの 1 点を小さな構造体に
  まとめ、時刻を整数で持つのはこのためである（[02](./02-core.md) §キャッシュ）。
- **ダウンサンプリングは見た目の情報量を保つ方式にする。** 等間隔の間引きにはしない
  （[02](./02-core.md) §ダウンサンプリング）。
- **web の配色は light のみにする。** Chart.js がダークテーマを持たないためである。

## gap / 検討中

- **web は 1 回の表示で多数のリクエストを並列に発射する。** core は接続ごとにスレッドを起こして
  並列に処理するが、同時に処理するのは 16 本までで、超えた分は枠が空くまで待つ
  （[02](./02-core.md) §REST API（現行））。コンテナが増えるほど待ち時間が伸びる。
  解消の本筋はリクエスト数を減らす bulk endpoint である。core の側は実装済みで、
  web の切り替えが計画中である（[02](./02-core.md) §計画中: web の切り替え）。
- **`benchmark/` は現行の構成と対応が取れているか要確認。** worktree を前提にした
  比較スクリプトで、保守の対象に含めるかを決めていない。
