# 03. web

web は Next.js（App Router）のアプリで、`next/` に置く。core の API からデータを取り、
Chart.js で描画する。

**実装済みの範囲**: 本章の内容はすべて実装済みである。古い core 向けの互換の経路
（§データ取得）の削除だけが計画中である。

## スタック

- Next.js 16 / React 19 / Turbopack
- Chart.js 4 + chartjs-adapter-luxon（時間軸）
- Tailwind CSS 4 + daisyUI 5（設定は `globals.css` に CSS で書く）
- zod（API レスポンスの検証）

## ページ構成

| パス | 実装 | 描画 |
|---|---|---|
| `/` | `next/src/app/page.tsx` | Partial Prerender（外枠は静的、チャートはストリーミング） |
| `/about` | `next/src/app/about/page.tsx` | 静的 |

`/` は 4 つのチャートをそれぞれ `<Suspense>` で包む。フォールバックは `ChartSkeleton` である。
1 枚の取得が遅くても、他のチャートと外枠の表示を止めない。

全体を `FilterProvider` と `ContainerColorProvider` で包み、4 枚のチャートが
フィルタの状態と色の割り当て（§色）を共有する。

## データ取得

🔒 **core の API を叩くのは Server Component だけである**（[01](./01-architecture.md) §通信の向き）。

**チャート 1 枚につき 1 リクエスト**である。core の `/usages/{kind}` が全コンテナ分の系列を
まとめて返す（[02](./02-core.md) §REST API（現行））。1 回の表示で core に送るのは 4 本である
（`/usages` を持たない古い core に対する動きは、§古い core 向けの互換の経路（一時的））。

- 取得関数は `next/src/lib/fetchers.ts` の `fetchUsages(kind)` の 1 つである。
  `kind` は `cpu` / `memory` / `io` / `net`。
- API の URL は環境変数 `API_URL` から読む。未設定なら `http://localhost:7878` を使う
  （dev で core を手元に立てたときの既定）。
- **core へのすべての fetch に、Cloudflare Access のサービストークンのヘッダを付けられる。**
  環境変数 `CF_ACCESS_CLIENT_ID` と `CF_ACCESS_CLIENT_SECRET` の**両方が空でない値で
  設定されているときだけ**、`CF-Access-Client-Id` と `CF-Access-Client-Secret` を付ける。
  どちらも未設定なら何も付けない（現状の本番と dev の動作）。片方だけの設定や、
  ヘッダとして送れない値のときは、ヘッダを付けず、サーバ側のログに警告を出す。
  組み立ては `next/src/lib/core-fetch.ts` の 1 か所で行い、`fetchUsages` と互換の経路の
  両方がそれを使う。**ヘッダを付けるリクエストでは、リダイレクトを追わない。** 独自のヘッダは
  別オリジンへのリダイレクトにも転送されるためである。3xx は「2xx 以外のステータス」として
  扱う（§古い core 向けの互換の経路（一時的））。ヘッダを付けないときは、これまでどおり追う。
  🔒 値はサーバ側でだけ読み、ログにも戻り値にも含めない
  （[04](./04-access-and-privacy.md) §web 側の準備（実装済み））。
- **core へのすべての fetch に期限を付ける。** 1 本につき **5 秒**である
  （`AbortSignal.timeout`）。core の手前の中継が、接続を受けたまま応答を返さない場合に、
  チャートの cache の充填が終わらず、スケルトンのまま待ち続けるのを防ぐ。
  - 期限は、応答のヘッダを待つ間と、**本文を読む間の両方**に効く。fetch を始めた時点から数える。
  - **互換の経路は、全体で 1 つの期限（10 秒）を共有する**（§古い core 向けの互換の経路（一時的））。
  - **期限切れは、接続の失敗と同じに扱う。** `/usages/{kind}` が期限切れになっても、
    互換の経路には切り替えず、失敗を返す。同じ宛先が応答しないので、試しても結果は変わらない。
  - 期限は、ヘッダと同じ `next/src/lib/core-fetch.ts` の `coreFetch` が付ける。
    **core へのリクエストは、必ず `coreFetch` で送る**（期限とヘッダを付け忘れた経路を残さない）。
  - 🔒 期限切れのエラーの文言は固定で、URL もトークンの値も含まない。
  - `/usages/{kind}` の期限切れのあとに互換の経路へは入らないので、1 枚のチャートが待つのは
    最長で 5 秒である。`/usages/{kind}` が 2xx 以外を返してから互換の経路に入った場合は、
    それまでの時間に最長 10 秒が加わる。
- レスポンスは zod で検証する。系列の `t` と `v` の長さが違う応答は、検証で失敗として扱う。
- 戻り値は `FetchResult<T>`（`{ ok: true, data }` または `{ ok: false, error: { message } }`）で、
  例外は投げない。**error 側は `Error` インスタンスではなく、シリアライズできる形にする。**
  `'use cache'` の境界を越えて返すためである。

各チャートの Server Component（`CpuChart.tsx` など）は、受け取った全コンテナ分を
Chart.js のデータセットに変換する。

- **コンテナの並びは web 側で決める。** コンテナ名を**コードポイント順**に並べ替える
  （`sortedContainerNames`）。core の並び（[02](./02-core.md) §REST API（現行））と同じ結果になるが、
  JSON のキーの順序には依存しない。ロケールに依存する比較（`localeCompare`）は使わない。
  この並びはデータセットと凡例の順序である。**色はここでは付けない**（§色）。
- 点は `{ x: t[i], y: v[i] }` である。**`x` は数値**（エポックからのミリ秒）で、
  Chart.js の時間軸にそのまま渡す。
- CPU とメモリは 1 コンテナにつき 1 本、IO とネットワークは 1 コンテナにつき 2 本
  （read と write、recv と send）のデータセットを作る。1 本目が実線、2 本目が破線である。

取得に失敗したときは、チャートの代わりに「取得中...」という文言を出す。
⚠ 失敗と取得中を区別しておらず、失敗の理由も画面には出ない。

### 古い core 向けの互換の経路（一時的）

**`/usages/{kind}` を持たない古い core に対しても表示できるようにしている。**
移行のための一時的な経路であり、**本番の core の更新後に削除する（計画中）**。
web と core は別々に配置されるので、どちらを先に配置しても動くようにするためである
（[05](./05-deploy.md) §本番の形）。

- `fetchUsages(kind)` は、まず `/usages/{kind}` を叩く。**応答が 2xx 以外のステータス
  だったとき**に、コンテナ別の API（[02](./02-core.md) §REST API（現行））から
  同じ内容を組み立てる。
- **ステータスは 404 に限らない**（403 や 5xx でも切り替える。サービストークンのヘッダを
  付けているときの 3xx も含む）。古い core の手前にある
  中継が、未知のパスに 404 以外を返す構成でも表示できるようにするためである。
  このため、`/usages` を持つ core が 500 を返した場合も、コンテナ別の API を試す。
- **次の場合は切り替えず、そのまま失敗として返す。**
  - 接続そのものの失敗（core が落ちている、名前を解決できない、など）。
    宛先が同じなので、試しても結果は変わらない。
  - 期限切れ（§データ取得）。応答のヘッダを待つ間でも、本文を読む間でも同じである。
    接続の失敗と同じに扱う。
  - 2xx だが本文が不正な場合（JSON として読めない、検証に失敗する、`t` と `v` の長さが
    合わない）。`/usages` を持つ core の不具合であり、別の経路に逃がして隠さない。
- **切り替えたときは、サーバ側のログに 1 行出す。** 種別と、きっかけになったステータスを含む。
  本番でどちらの経路が使われているかを、配置先のログで確かめるためである。
  チャートは 10 秒 cache されるので、出る量は限られる。
- 組み立ては次の順に行う（`next/src/lib/fetchers-legacy.ts`）。
  1. `/containers` で名前の一覧を取る。
  2. 種別に応じて、コンテナ別の API を `Promise.all` で並列に叩く。CPU とメモリは
     1 コンテナにつき 1 本、IO とネットワークは 2 本（read と write、recv と send）である。
  3. 各要素の `time` を `Date.parse` でミリ秒に直して `t` に、値を `v` に入れる。
     値が無い要素は `null` にする。**`time` を解釈できない要素と、ミリ秒に直した値が
     0 以下の要素は捨てる**（core が時刻を読むときと同じ基準。[02](./02-core.md) §収集）。
     Docker が時刻を持たないときに返す `0001-01-01T00:00:00Z` は、解釈はできるが負の値になる。
     残すと横軸が西暦 1 年から始まる。
- **返す形は `/usages/{kind}` と同じ**（コンテナ名 → 系列名 → `{ t, v }`）で、同じ検証を通す。
  並べ替え、データセットへの変換、色は共通で、チャートの Server Component に分岐は無い。
- どれか 1 本でも失敗したら、全体を失敗として返す。
- **この経路の全リクエストで、1 つの期限（10 秒）を共有する。** `/containers` を叩く前から
  数え始める。各リクエストは、1 本ごとの期限（5 秒）と、全体の残り時間の**短い方**で
  打ち切られる。全体の期限を過ぎたあとのリクエストは、送らずに失敗する。
  期限切れも、全体の失敗である。
- 互換の経路の中では cache を宣言しない（§キャッシュ構成）。
- **1 回の表示で core に送るリクエストの数**は、`/usages` を持つ core なら 4 本である。
  古い core では、失敗する 4 本に加えて、`/containers` とコンテナ別の API
  （`6N` 本。N はコンテナ数）を叩く。`/containers` は 4 枚のチャートがそれぞれ叩くので
  最大 4 本で、計 `4 + 4 + 6N` 本以下になる。

## キャッシュ構成

`next.config.ts` で `cacheComponents: true` を有効にしている。

- **各チャートの Server Component が cache の単位である。** 冒頭で `'use cache'` を宣言し、
  取得・整形・JSX の構築までをまとめて cache する。
- 寿命は `cacheLife({ revalidate: 10, expire: 60, stale: 10 })` である。core の収集間隔
  （10 秒）に合わせている。
- タグは `chart:cpu` / `chart:memory` / `chart:io` / `chart:net`。
- 取得関数（`fetchUsages`）は cache を宣言しない（チャート側の cache に含まれる）。
  4 枚のチャートが共有する取得は無く、`containers` というタグも無い。

🔒 **不変条件**: cache される関数の中で、リクエストごとに変わる API（`cookies()`、`headers()`、
`searchParams` の await など）を呼ばない。

## チャート

`next/src/components/Chart.tsx`（Client Component）が Chart.js を包む。

- 折れ線で、点は通常は描かない（ホバー時だけ出す）。アニメーションは無効。
- **横軸は時刻**。目盛の単位は Chart.js に自動で選ばせ、目盛の境界に合わせて範囲を広げる
  （`bounds: 'ticks'`）。24 時間なら 1 時間刻み、短い範囲なら分刻みで、
  キリのよい時刻に目盛が来る。表示は `HH:mm` である。
- **縦軸は 0 始まり**で、上限は自動である。
- **データが途切れていた区間は、線が切れる。** コンテナや core が止まっていた間を、
  前後の点を結ぶ直線で埋めない。core が `/usages/{kind}` の途切れの位置に `null` の点
  （目印）を挟んでおり（[02](./02-core.md) §REST API（現行）の途切れの目印）、
  Chart.js の折れ線は `y` が `null` の点で切れる（`spanGaps` は既定の無効のまま）。
  web は目印を特別扱いせず、ほかの点と同じく `{ x, y }` にするだけである。
  途切れの判定は core が持つ。
  - 値が取れなかった点（`null`）でも、同じく線が切れる。
  - ⚠ **古い core 向けの互換の経路（§データ取得）では、従来どおり直線で結ばれる。**
    コンテナ別の API は目印を返さないためである。
- **ツールチップはホバー位置に最も近い 1 点だけ**を出す（`mode: 'nearest'`、`intersect: false`、
  `hitRadius: 10`）。全コンテナ分を並べると読めないためである。
- データセットには `containerName` を持たせ、フィルタと凡例の対応付けに使う。
  Chart.js の型は `next/src/types/chartjs.d.ts` の declaration merging で拡張している。
- Chart.js 標準の凡例とタイトルは使わない。タイトルは HTML の `<h3>` で出し、
  その下に自前の凡例を置く。
- 時刻はブラウザのタイムゾーンで表示される（core が返すのはエポックからのミリ秒）。

⚠ データセットが変わるたびに Chart.js のインスタンスを作り直している。
フィルタの切り替えと色の変更（§色）は作り直さず、`update('none')` で反映する。

## 凡例兼フィルタ

`next/src/components/MiniLegend.tsx` が、各チャートの上端に**色の点とコンテナ名のチップ**を並べる。
凡例とフィルタを兼ねる。チップの色は、線の色と同じ関数から取る（§色）。

| 操作 | 結果 |
|---|---|
| クリック / タップ | そのコンテナの表示・非表示を切り替える |
| ダブルクリック / ダブルタップ | そのコンテナだけを表示する。すでに単独表示なら全表示に戻す |

- ダブルの判定は「同じチップへの 250ms 以内の 2 回目」である。この判定のため、
  **シングルクリックの反映は 250ms 遅れる**。
- **ダブルを処理してから 250ms 以内の、同じチップへのクリックは捨てる。** 3 連打の 3 回目が
  新しいシングルになり、単独表示にしたチップ自身を隠す（全コンテナが非表示になる）のを
  防ぐためである。期間はダブルの時刻から数え、捨てたクリックでは延ばさない。
  別のチップへのクリックは、通常どおり扱う。
- **反映を待っているシングルがあるときに別のチップが押されたら、待っていた分をその場で
  反映する。** もうダブルにはなりえないためである。遅らせたままにすると、あとから押した
  チップのダブルと順序が入れ替わる（先に単独表示になり、そのあとで前のチップが切り替わる）。
- **Enter の押しっぱなしによるキーリピートは、クリックとして扱わない。** 押し始めの 1 回だけが
  クリックになる。
- 判定は、時刻を引数に取る純粋な関数（`next/src/lib/legend-click.ts`）にある。
  タイマーの予約と取り消しは `MiniLegend.tsx` が行う。
- IO やネットワークのように 1 コンテナに 2 系列あるチャートでも、チップは 1 コンテナにつき 1 つである。
- チップは `<button aria-pressed>` で、非表示のものは薄く、打ち消し線を付ける。
- iOS のダブルタップズームを抑えるため `touch-manipulation` を付ける。

### フィルタの状態

`next/src/components/FilterContext.tsx` が、非表示のコンテナ名の集合（`hidden`）を
**唯一の状態**として持つ。

```ts
const { hidden, toggle, setAll, isolate, clear } = useFilter();
toggle(name);             // 1 件の表示・非表示を切り替える
setAll(names);            // hidden を names に置き換える
isolate(name, allNames);  // name 以外を非表示にする
clear();                  // 全表示に戻す
```

**状態は React の state だけで持ち、URL にも保存先にも残さない。** リロードすると全表示に戻る。

## 色

**色は、画面全体で 1 つのコンテナ名の一覧から決める。** 一覧は 4 枚のチャートが持つ名前の
**和集合**で、これを**アルファベット順**（コードポイント順。§データ取得と同じ比較）に並べ、
その位置に Tableau 10 の配色を順に割り当てる（`next/src/lib/colors.ts`）。
core が返す順序には依存しない。

- **割り当てはクライアント側で行う**（`next/src/components/ContainerColorContext.tsx`）。
  Server Component が作るデータセットは色を持たない。
- 各チャート（`Chart.tsx`）は、自分が持つコンテナ名を Context に登録する。
  Context は全チャートの登録の和集合から、名前ごとの位置を決める。
  チャートが画面から外れたら、その登録を外す。
- **同じコンテナは 4 枚のチャートで必ず同じ色になる。** 4 枚は別々に cache された応答を
  描くので、コンテナが増減した直後は、チャートによって持っている名前が違いうる。
  チャートごとの一覧で色を決めると画面内で色が食い違うため、和集合で決めている。
- **線の色と凡例の色は、同じ関数から取る。** `Chart.tsx` が Context から受け取った関数を
  Chart.js のデータセットに当て、同じ関数を `MiniLegend.tsx` に渡す。
- 和集合が変わったとき（あとから届いたチャートが新しい名前を持っていた場合など）は、
  全チャートの色が同時に変わる。Chart.js のインスタンスは作り直さず、
  `update('none')` で反映する。
- **ハイドレートが済むまでは、必ずそのチャート自身の名前一覧での位置で描く**（和集合を見ない）。
  サーバでは登録が走らないので、サーバが出す HTML は必ずこの色である。先にハイドレートした
  別のチャートの登録が和集合に入っていても、最初の描画をサーバの HTML と一致させる。
  React は属性の食い違いを直さないので、食い違うと凡例の点だけがサーバの色のまま残り、
  線の色とずれる。
- ハイドレートのあとは和集合での位置に切り替える。和集合にまだ無い名前（登録が反映される前）
  には、そのチャート自身の名前一覧での位置を使う。
  全チャートが同じ名前を持つ通常の場合は、どの段階でも同じ色になり、切り替えで色は変わらない。
- 並べ替えはコードポイント順なので、大文字で始まる名前は小文字で始まる名前より前に来る。
- コンテナが 10 個以下なら色は衝突しない。11 個目からは同じ色が巡回する。
- ⚠ コンテナが増減してアルファベット順の位置が変わると、既存のコンテナの色もずれる。
  これは受け入れている。

## テーマ

**light のみ**である。`globals.css` で daisyUI のテーマを `light` に固定し、
`<html data-theme="light">` を指定している。Chart.js がダークテーマを持たないためである。
